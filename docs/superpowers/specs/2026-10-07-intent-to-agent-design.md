# 意图识别到 Agent 接收：设计确认稿

日期：2026-10-07。状态：用户明确要求无需再确认、直接实施，已完成JEV、路由与多Agent协作判断，终点为Agent输入准备。实现与实测见 `docs/意图路由与多Agent协作.md`，下面保留设计依据。本文承接十项独立相关性判断、通用Agent兜底与统一基础Agent。

## 1. 本次终点

实现“用户输入 → 三路意图判断 → 程序路由 → 对应 Agent 实例接收并准备输入”。输出应能看到选中了谁、为什么、给该角色哪些提示和工具权限。不会调用回答模型、执行工具、查询 RAG、生成业务答案或合并多个回答。

专业 Agent 只改变角色提示词和允许工具，不各写一套决策流程。通用 Agent 同样继承基础 Agent，承担接待、边界说明和不清楚时的澄清；不增加专用澄清 Agent。

## 2. 当前代码与要补的前提

- 现有 JEV 是一次请求的 dialogue 四选一、clarity 是非题、intent 九类单选，不是十项独立判断。
- 两路模板检索已支持业务45条＋非业务C10的30条，共75条；C10只是匹配证据，不是已经建立的路由。
- 现有融合仍是九类加权基线，完整“JEV主判、两路辅助”的四项测试尚未通过。不能将它直接视为新路由的可靠契约。
- 项目尚无 Agent 或 LangGraph 子系统；当前 Miniconda 环境未安装 langgraph / langchain-core。项目不是 Git 仓库，不会为本文创建仓库或伪称已提交。

因此推荐先补齐独立判断及辅助证据契约，再接路由，不临时用旧单选分差模拟多意图。

## 3. 方案取舍

1. 推荐：十项独立 JEV 判断＋独立清晰度，另外两路保留候选证据；LangGraph 管状态流转，程序决定角色。符合已讨论的复合诉求和通用兜底规则。
2. 先用现有九类单选接路由：改动少，但与已确认的独立相关性方案不符，两个诉求仍竞争同一份概率，本次不采用。
3. 让另一个 LLM 自由选角色：额外调用且更难解释，重复了意图识别工作，本次不采用。

## 4. 十项判断与两路辅助

JEV 对 C01–C09 分别问“本轮是否包含此类实际业务诉求”，对 C10 问“本轮是否为不包含投稿业务诉求的非业务交流或范围外请求”；保留独立 clarity 是非题。C10不包含“业务领域明确但具体需求不清”、无指代句或服务失败。问候后接业务问题，不因问候判整条非业务。

每项 noul 是“是”的模型概率，十项不要求总和为1，不从分差生成分类 confidence，不宣称这些概率已校准。复合业务允许多个类别同时高分。

按此前核对的网关每次最多8个问题，将11个问题分为两批（clarity＋C01–C05共6题；C06–C10共5题），使用同一份当前消息与最近六条历史。两批可并发，各自有请求ID，报告合计用量与两批状态；不自动重试。任一必需判断失败或响应缺失都不能用其余题补成完整成功结果，应交给通用 Agent，保留明确的技术失败原因。用户取消应传播，不伪装降级结果。

Embedding / BM25继续共享75条例子，分别输出十类原始分、命中示例及匹配排名。它们只提供支持、替代候选、并列候选、无正匹配等诊断信息，不提高 JEV 的原始概率，不独立确认业务性质。辅助分歧先记录、不硬否决清晰且高相关的JEV判断，避免噪声检索反复把明确诉求拉回兜底。

现有0.7/0.2/0.1融合分保留为历史／诊断基线，不作为新路由的正确概率。迁移时让当前未完成的辅助证据测试与新契约一致，修复对应功能，而不是删掉或跳过报错测试。

## 5. Agent 划分：推荐五个角色

| 类 | 角色 | 意图映射 |
|---|---|---|
| GeneralAgent | 通用接待、澄清、范围说明及失败兜底 | C10及所有无法可靠分流的情况 |
| SubmissionRequirementsAgent | 期刊范围、格式、投稿材料 | C01、C02、C03 |
| EditorialWorkflowAgent | 平台操作、审稿返修、撤稿转投申诉 | C05、C06、C09 |
| PublicationPolicyAgent | 伦理署名、录用后出版及版权政策 | C04、C08 |
| PublicationFeesAgent | 费用、减免、支付退款 | C07 |

所有角色直接继承 BaseAgent。GeneralAgent是一个兜底角色，不作为其他专业角色的父类，以免专业角色意外继承接待话术。角色类只提供不同 profile / system_prompt / allowed_tool_names，共享输入准备逻辑；未来共享的模型与工具调用循环也应放在 BaseAgent，不在专业类重复实现。

C08全部归出版政策角色，本次不再拆分制作流程与版权子路由。同一角色覆盖多个意图，不代表一个意图可以任意分到多个角色。

## 6. 路由规则

路由是确定性的程序，不是又一个 LLM Agent。实验默认参数拟设：需求清晰门槛0.75、单项业务及非业务相关门槛0.80；均可配置，并在输出记录所用配置。这些是待评测起点，不是业内标准，也不证明已达到可靠准确率。

按以下顺序处理：

1. 判断服务不可用、结果缺失或协议异常：GeneralAgent，原因 recognition_failed；不能声称用户一定不清楚。
2. C10达到门槛且无高相关业务项：GeneralAgent，原因 non_business；准备接待或范围说明，不因clarity低分强行追问。
3. C10与业务项同时达到门槛：GeneralAgent，原因 conflicting_judgments；不靠辅助相似度强行解决语义冲突。
4. clarity低于门槛：GeneralAgent，原因 unclear_request；准备针对缺失对象或诉求澄清，不猜业务答案。
5. 清晰但没有业务项达到门槛：GeneralAgent，原因 uncertain_intent；保留候选以帮助澄清，不硬选检索第一名。
6. 清晰且有高相关业务项：按上表映射专业 Agent；同一角色去重，保留它对应的全部意图。跨角色复合诉求记录多个专业角色，本轮只准备各自输入，不执行并行工具或答案汇总。

例如格式＋材料只选一次SubmissionRequirementsAgent；格式＋费用准备Requirements和Fees两个Agent。多项独立高分不应自动当成“不明确”。

多 Agent 协作判断以去重后的专业角色数量为准：数量大于1时 multi_agent=true、mode=multiple，否则为false。只有已通过清晰度与相关性检查、且不存在C10冲突的业务诉求可以触发；辅助路径分歧、同角色多意图、模糊分类均不能自行触发。decision保存每个角色对应的intent_ids及协作原因，各Agent输入包含原始消息与该角色负责的意图，不另调用LLM拆解子问题。本次完成协作决策与输入准备，不声称完成协作执行、最终答案汇总或依赖任务调度。

## 7. 数据与图的边界

请求对象保存本轮message、history和request_id，不在本次引入长期用户画像、强制user_id或记忆数据库。

判断结果保存独立intent_probabilities、clarity_probability、三路原始数据、辅助证据、调用状态和用量。分数类型必须显式标识，独立是非概率不得当成互斥单选概率归一化。

RoutingDecision保存选中的agent_types、matched_intents、single／multiple／fallback模式、fallback_reason和使用的实验参数。Agent准备结果保存角色静态提示、本轮消息和历史、允许工具标识与实际已注册工具。角色静态提示与动态请求材料分开放，不把每次变化的消息写进静态角色提示。

LangGraph只编排以下阶段：

```text
START → recognize_intents → route_agents → prepare_selected_agents → END
```

每个阶段更新明确的state字段，不能把整个历史工具轨迹当成路由输入。完整图是识别到角色接收，不是已经跑通的回答Agent。多角色阶段准备一个角色输入列表，不假装已经完成多Agent协作。

工具权限必须通过注册表过滤，不只写在提示词里；未注册的工具不能出现在真实模型tools列表中。当前RAG尚未封装为Agent工具，所以专业角色只定义相应检索能力的允许标识，实际工具列表为空，并报告未绑定状态。不同角色可预留要求／流程／政策／费用检索工具，不能伪造查询已经执行。

## 8. 实现与验证范围

后续实现预计涉及独立JEV契约、三路辅助证据、routing模块、agents基础类与角色配置、LangGraph入口、路由CLI及对应离线测试。原RAG、资料库、解析结果和.env密钥保持不变。依赖仅安装到用户现有ieee-submission-assistant Miniconda环境，记录实际验证的LangGraph版本到environment.yml，不另建Python环境。

离线验收覆盖：11题分批与完整性、独立概率不归一化、服务失败与取消、非业务C10、含糊业务、指代与历史输入、明确单业务、同角色多意图去重、跨角色复合诉求、缺少证据不等于意图不明、通用兜底原因、所有角色继承同一个BaseAgent、静态提示与动态材料分离、工具权限与未注册工具、完整图停在准备输入后。

CLI提供无需密钥的受控判断结果模式，能够演示路由及Agent接收；真实识别模式使用现有本地配置，明确告知会产生JEV两批及Embedding调用。验证需报告完整回归结果，不把旧遗留报错隐去。真实付费烟雾测试控制在少量合成案例，不为追求高分批量试调。
