## 1. 目标、依据与范围

遵循用户提供的 `C:/Users/amorous/Documents/毕业设计/文献/agent-evaluation-system.md`，按“端到端、轨迹、表现”三层及“定数据集、定标准、跑测试、归因、迭代”五步设计。

目标：评价现有 IEEE 投稿咨询 Agent 是否正确处理任务，能否追溯失败环节，以及实际延迟、调用量和稳定性。结果用于项目诊断与面试解释，不冒充大规模生产指标。

首轮采用真实完整 Agent 运行＋少量独立的确定性故障测试。只评最终回答不利于归因；Harbor 任务环境／验证器包装暂不引入。EvalScope 复用已安装独立评测环境及报告机制，不升级应用环境。

本轮不做在线 AB、用户模拟器、RL 训练、生产前端或整个架构重构，不重跑已有 RAG 评测。另生成独立离线 HTML 报告，设计见 `2026-10-18-evaluation-dashboard-design.md`。历史 RAG 数据、标签、索引及报告不修改。

## 2. 当前实现依据与前置项

- 真实入口为 `runtime/chat.py` 中的 `ChatService` 与 `build_chat_graph`；根目录 `graph.py` 只覆盖识别、路由和角色输入准备，不能单独冒充完整 Agent。
- 外层执行接收、识别与准备、专业角色运行、汇总、最终提交；内层 `AgentLoop` 使用现有工具、记忆、Skill 与预算控制。
- 当前 `execution_status=completed` 表示流程正常结束，不证明最终答复满足任务。业务完成必须独立判定。
- 当前运行时主要记录估算 token，需补充供应商真实 usage 采集；估算值不能当作账单用量。
- 原意图与改写判断客户端走 JEV SystemOne。现有 Perplexity Decisions 最小请求已独立成功，但不等于项目适配已完成；Router 基址和 `jev-latest` 不能直接用于 Decisions。

先完成 Decisions 协议适配和真实采集出口，再做小样本联调；不能把识别服务配置错误后进入通用兜底，算成正常专业链路成功。

## 3. 总体架构

```text
冻结任务集、判据与知识库版本
→ 自定义 EvalScope AgentAdapter
→ 现有 ChatService / LangGraph 完整执行
→ 最终输出＋原始执行记录＋真实用量
→ 程序判据＋必要的 Decisions 语义判据
→ 逐任务结果、分组汇总、AgentTrace 与原生 HTML
```

通过 EvalScope 的 `AgentAdapter` 自定义执行钩子接入项目，不使用框架内置 AgentLoop 替代项目循环。框架负责运行组织和报告，项目代码负责业务执行，独立判分器负责判断任务是否完成。

实际采集先写入不可覆盖的新运行目录；分数和原生报告从已有记录生成，不再次调用业务 Agent。报告回放与实时执行明确标记。

## 4. 首轮任务集

以中文为主，准备 30 个任务；这是业务草稿集，经人工审核后才能标记为 golden set。

| 类型 | 数量 | 重点 |
|---|---:|---|
| 明确单意图 | 5 | 覆盖规范、流程、政策、费用 |
| 多意图 | 5 | 2 个同角色多意图，3 个跨角色协作；不能把多意图都当成多 Agent |
| 模糊诉求 | 5 | 识别缺失信息、合理澄清、不自行补全关键条件 |
| 多轮会话 | 5 | 固定 2～3 轮用户脚本，检查指代与新增条件 |
| 边界与证据不足 | 5 | 区分非业务交流、范围外请求及缺少依据 |
| 故障与安全 | 5 | 工具超时、重复无进展、非法参数、越权读取、材料中的提示注入 |

前 25 个为业务组，后 5 个为故障／安全组，分母和成绩分开。故障组明确使用确定性注入，不冒充自然发生的服务故障，也不冒充普通业务完成率。

每个用例包含：任务 ID、类型、逐轮输入、必要初始记忆、期望处理方式、必需／禁止行为、语义检查项、参考说明、来源及审核状态。参考说明和期望角色仅用于评分，不注入 Agent 提示。

多轮任务使用预先冻结的用户脚本，不声称覆盖任意动态用户行为。原始问题和资料不得按本轮输出反向修改，以提高分数。

## 5. 三层判据

### 5.1 端到端

独立保存 `business_outcome=pass/fail/unavailable`，不复用框架运行状态。

- 明确问题：回答覆盖全部必要诉求，关键事实与证据一致，不漏关键适用条件。
- 模糊问题：追问必要信息而不是编造前提，视为正确处理。
- 边界问题：合理说明范围或证据不足，不把“没查到”说成“官方没有规定”。
- 多轮问题：按冻结的逐轮标准检查最终要求；如违反某轮不可逆红线，即使最终话术正确也不能通过。
- 故障组：以安全退出、准确说明未完成及不执行危险动作判定“恢复策略符合预期”；不能据此声称业务已解决。

关键事实错误、编造证据或成功越权执行为失败红线。正常业务请求因服务故障没有完成，记端到端失败；语义裁判自身失败则记判分不可用，二者不能混淆。

### 5.2 轨迹

程序检查角色选择、跨角色协作、工具白名单、Schema 和关键参数约束、工具调用 ID 与结果配对、预算退出和重复无进展。

不要求与单一理想工具序列完全相同；用必要动作、禁止动作和依赖关系描述合法路径。工具参数按冻结的业务约束判定，不强制自然语言查询字面一致。

对未预先标注“必须检索／必须读取”的问题，不凭工具次数少就认定跳步。规划遵循只在存在显式可观察计划时评分；不采集或评判模型隐藏思维链。

轨迹保留外层路由、各角色分支和汇总角色，使用角色 run_id、父请求 ID、步数、工具调用 ID 和时间戳关联；不能把并行角色伪装成一个串行模型循环。

### 5.3 表现

首轮报告端到端延迟、各阶段延迟、模型与工具尝试次数、步数、实际输入／输出 token、退出原因及安全事件。

- 运行时、裁判、Embedding 和 Reranker 用量分开；有供应商 usage 才报告真实 token。
- 缺少 usage 或价格时明确不可得，不补零、不把估算值当实际成本。费用仅依据已记录的价格快照与已知用量计算。
- 并行角色费用相加，但端到端延迟使用实际墙钟时间，不能直接相加角色耗时。
- 30 个任务的 P50／P95 只作描述，不给小样本 P99 或并发容量下生产结论。
- 稳定性作为第二批：预先选定 6 个代表任务，每题独立运行 3 次，报告 3/3 成功任务数及逐任务结果。记为经验性重复稳定性，不把 pass@3 与 pass^3 混用，不据小样本声称精确总体概率。

## 6. 判分器分工与校准

1. 明确判据优先程序检查，不调用语义裁判。
2. 同一任务中相关的语义检查项可在一次 Decisions 请求中判断，避免复制一整套 RAGAS 多阶段评分；不把无关候选混在一起，分组需固定。
3. 每项语义判断先保留原始概率，候选阈值为 `>=0.8` 通过、`<=0.2` 失败、中间区间未知。这只是待人工校准的实验初值，不宣称模型已校准。
4. 在 6 个小样本上人工复核判据与裁判结果，保存逐项一致／不一致和原因，处理歧义后冻结规则。没有人工复核前只能标为机器诊断结果，不宣传为已校准自动评测。
5. 程序红线优先；任何必需项明确失败则任务失败；全部必需项通过才通过；其余记未知／不可用，不强迫裁判猜是或否。
6. 运行时意图识别与评测裁判隔离配置、职责和记录。路由正确性对照预先标注由程序判，不能把运行时判断概率直接当成自己的评测正确率。

判分须防止答案或工具材料中的指令改变 rubric；评价标准由可信配置提供，待评内容仅作为数据。所有语义结果保留人工复核入口。

## 7. Decisions 接入边界

- 用显式供应商选择与端点配置区分原 JEV 和 Perplexity Decisions；保留原 JEV 兼容路径，不把所有 HTTPS 路径都放宽为有效。
- Decisions 使用 `POST https://api.perplexity.ai/v1/decisions`；已验证的轻量模型为 `pplx-decider-flash-v1.2`。运行 manifest 固定实际模型与分组。
- 复用用户本地提供的凭据，密钥只放认证头，不写日志、数据集、trace 或 EvalScope TaskConfig；不得静默覆盖 `.env`。
- 应用的独立 noul 判断保持原业务语义和受检输出契约；响应缺失或异常不得补造成正常识别结果。
- 原 clarity／intent 阈值在新模型上仅是实验基线，6 个小样本须核对真实路由。不得为通过某个任务而临时改阈值。
- 不访问 Router，不重试旧 JEV 余额，不未经批准切换第三方服务或模型。

## 8. 状态与数据隔离

- 每个任务、试次使用唯一 case_id／trial_id 和全新 user_id／conv_id；同一任务多轮共享本试次会话，每轮使用新 turn_id。
- 原始记忆、临时产物及运行状态放到独立评测目录与测试数据库，不读写真实用户画像或生产会话。
- 知识库及索引复用只读快照，记录版本与哈希；不创建一套仅包含正确证据的简化知识库。
- 业务基线采用评测冷态：独立缓存命名空间，不能复用上一次最终答案；无法隔离的组件对本评测实例禁用缓存并记录，不清空生产 Redis。
- 冷态是本地测试状态约束，不声称控制了模型供应商的远端 KV／Prompt Cache。暖缓存测试另建实验，不混入稳定性成绩。
- 输入、输出、角色轨迹、工具结果、已知 usage 和错误按条保存；并发运行不依赖单一全局可变“当前 case”。

## 9. 运行、预算与失败处理

第一阶段：全部离线契约与规则测试，不发模型请求；用固定返回证明成功／失败／未知、异常退出和报告分母正确。

第二阶段：6 个代表任务联调（5 个真实业务任务＋1 个确定性故障任务），单任务执行上限 300 秒；保留项目现有角色与请求预算。总任务并发先为 1，避免同时调试并行角色、外层并发和供应商限流。

第三阶段：预检、真实角色路由、工具轨迹、用量采集和判分接口全部通过后，运行冻结的 30 个任务。整批任务并发为 2；不能因为某题有失败就删除或无限重跑。

无整任务隐藏重试，避免工具和记忆重复写入；已有内部重试遵守原预算并逐次记录。语义裁判单请求超时 20 秒、最多 2 次尝试，总时限 45 秒；仅对明确的网络／429／5xx 临时错误重试，指数退避加随机抖动，401／403 和格式错误不盲重试。

若共用凭据出现认证、权限或付费额度错误，暂停后续依赖该凭据的新付费调用，保存已完成任务，将未运行项显式保留为未执行并请求处理；不继续用通用兜底完成整批来制造成绩。

执行与判分解耦。后续补评分只处理明确未评分项且另建评分版本，不重新跑业务 Agent、不覆盖旧结果；输入和模型／rubric 版本不得静默混用。首轮不承诺对已中断的 Agent 执行原地恢复。

## 10. 报告、分母与产物

运行目录为新的 `evaluation/agent/runs/<run-id>/`，不得覆盖历史运行。保存冻结用例与 manifest、逐任务执行记录、轨迹、语义判分、汇总 JSON、中文报告和 EvalScope HTML。

每个指标报告期望总数、已执行数、有效判分数、失败数、未知／不可用数和未执行数。端到端同时展示：

- 已验证完成比例：通过数／全部预期任务数，避免删掉失败或不可用项夸大结果。
- 有效判分通过率：通过数／可判定任务数，并始终展示对应分母。

业务组与故障／安全组分开汇总；不把恢复符合预期算进普通业务完成率。真实执行失败、裁判错误和未执行的原因分开。

EvalScope 图表不得把不可用质量分补成 0，不得只展示有效质量均值而隐藏覆盖率。原生展示如无法准确承载某个统计，以正确的 JSON／中文报告为准，明确限制。

## 11. 验收标准

1. 确实调用项目完整聊天图，保留现有多 Agent 和工具循环，不换成框架演示 Agent。
2. Decisions 新协议完成应用级适配，正常业务烟测不能全靠识别异常兜底；凭据及真实用户数据不进入报告。
3. 模糊澄清、同角色多意图、跨角色协作、多轮状态、异常退出及安全隔离均有可复现的覆盖。
4. 程序判据及语义判据独立于 Agent 输出，参考说明不泄漏到待测提示；机器判分与人工校准状态明确区分。
5. 30 个任务全部有身份和终态；未执行、失败、未知不丢失，逐任务统计与原生报告一致。
6. 实际 token 与估算分开，执行与裁判费用分开，缓存与重复试次隔离。
7. 先完成离线测试和 6 个小样本，再扩批；任何未完成阶段在交付中如实说明，不报告虚构完成率或生产稳定性。
