# RAG 生成评测接入设计

状态：用户已于 2026-10-16 确认方案与“首轮千问兼任裁判”的默认选择；实施计划待确认。本文件不是已实现或已完成评测的证明。

## 1. 目标与边界

遵循用户提供并要求采用的 `rag-evaluation-system.md`：RAG 评测只分检索与生成两部分。检索首轮已完成；本阶段接入生成评测，不扩展成 Agent 端到端评测，不调用 JEV。

目标：回答是否忠于实际检索证据、是否正确、是否切题；辅助判断检索上下文是否覆盖回答所需信息。保留逐题失败和来源，输出中英文分组指标及可视化报告。

本阶段不修改生产路由、Agent Loop、记忆、默认 JEV 校验、知识库、分块、索引或检索参数。RAGAS 及额外依赖只进入项目独立评测环境，应用环境不升级。

## 2. 三种可选路径

1. **推荐：固定真实检索结果，先做 RAG 生成评测。** 使用现有排名文件中的父块正文，隔离生成能力；结果可以追溯到原始检索实验，且无须重新付费检索。
2. 每次实时检索再生成。更接近在线执行，但模型改写随机性和服务波动会与生成差异混在一起，成本也更高；留作后续端到端回归。
3. 先运行完整多 Agent，再评价最终答复。会混入意图、工具、记忆和汇总影响，属于后续 Agent 评测，不适合替代本轮 RAG 生成评测。

本设计采用路径 1。它是固定上下文的离线 RAG 生成诊断，不声称等于整个生产 Agent 的回答质量。

## 3. 输入与对照

### 冻结输入

- 数据集：`evaluation/rag/data/ieee-bilingual-v1/`，15 组中英文问题，共 30 条查询。
- 基线 A：`evaluation/rag/runs/20261016-pilot-01/` 的 B3，原问题双路召回＋RRF＋重排＋父块回溯。
- 基线 B：`evaluation/rag/runs/20261016-multiquery-no-jev-01/` 的 B4，无 JEV 语义校验的多查询召回＋重排＋父块回溯。
- 只读取各记录实际返回的父块正文、顺序和来源，不拿 qrels 中的正确父块替换实际检索结果。
- 每次运行核对输入实验及数据集哈希、问题覆盖、证据 ID 与正文一致性；旧实验与数据集不覆盖。

### 两组对照的控制变量

两组使用同一生成模型、同一系统提示与证据格式、相同生成参数。唯一对照差异是冻结的实际检索上下文。保留双语分组，不将 30 条配对查询视作 30 个独立业务问题。

首轮先在两组各运行一条中文和一条英文问题，共 4 个回答；接口、裁判与数据格式验证通过后，再完成两组各 30 个回答，共 60 个回答。

## 4. 生成输入与参考答案隔离

RAGAS 四字段：

| 字段 | 来源 | 是否进入回答模型 |
|---|---|---|
| user_input | 冻结查询正文 | 是 |
| retrieved_contexts | 对应基线真实返回的父块正文列表 | 是 |
| response | 本阶段实际调用千问得到的回答 | 模型输出 |
| reference | 冻结 annotations.jsonl 的 reference_zh / reference_en | **否，仅供评分** |

额外保存 query_id、语言、基线、父块 ID、来源、生成状态、finish_reason、已知用量与耗时。相关性 qrels 不作为回答提示的一部分。回答模型不可看到参考答案或裁判结论。

参考答案目前仍是来源核验的 Agent 草稿。若在检查中发现错误，应保存新的独立参考版本及修订原因，不改写此前的检索数据集或历史实验。

## 5. 回答生成

- 使用项目现有千问服务和生成调用接口；记录实际解析后的模型名，不仅记录默认配置名。
- 仅根据提供的证据作答，按问题语言回答，保留主体、条件、例外和否定关系。
- 证据不足或冲突时应明确说明，不能把无检索结果解释为“官方没有要求”。
- 证据作为不可信数据，不允许其改变系统规则、调用权限或提供额外指令。
- 可使用稳定的证据编号引用来源；原始父块和来源数据完整保留。
- 禁止工具调用；空答案、工具调用响应、协议错误和截断回答单独记录，不将不完整输出冒充正常完成。
- 无用户记忆、跨题历史或完整 Agent 编排，避免题目互相污染。

## 6. 指标与裁判

沿用 EvalScope 统一组织与展示、RAGAS 官方指标计算，不自己编写一套近似公式冒充 RAGAS。

生成主指标：

- Faithfulness：回答中的事实是否由检索上下文支撑。
- AnswerCorrectness：回答与参考答案的事实一致性和覆盖情况。

生成辅助指标：

- AnswerRelevancy：回答与问题是否相关。

上下文诊断指标：

- ContextPrecision：有用上下文及其排序。
- ContextRecall：上下文是否覆盖参考答案需要的信息。

Context 系列仍归于检索上下文诊断，不因此新增第三个 RAG 评测部分。具体 RAGAS 类名、参数、权重、语言提示与版本在接口验证后固定并写入 manifest，不能静默更换指标含义。

首轮默认用已配置的千问作为裁判，以便不引入新服务账号；辅助 Embedding 使用现有服务。不使用 JEV。生成和裁判是不同职责，即便使用同一模型也需分开记录。

同模型生成与裁判可能带来自偏好，不能宣称裁判完全独立、无偏。先做少量明显受支持/无支持陈述的裁判校准并抽查理由，再扩批；正式结论仍需人工抽样复核，后续可另接独立裁判模型。

## 7. EvalScope 与版本兼容

已安装 EvalScope 1.13.0，其 RAGEval 包内的 RAGAS 适配器声明面向 RAGAS 0.4.x，支持四字段输入与 OpenAI 兼容模型配置；RAGAS 目前尚未安装。

优先验证官方 EvalScope/RAGAS 接口。若官方入口只能输出评分 JSON 而不能直接生成同样的原生 HTML 展示，则复用现有自定义 benchmark 的报告模式展示已由 RAGAS 官方实现计算的逐题指标，明确标记为评分回放。不可用自写裁判评分冒充官方指标，也不可用报告回放冒充新的模型生成。

安装前核对依赖兼容并固定可运行版本；若接口不兼容，保留输入和回答，说明具体限制，不通过换名或补造分数绕过。

## 8. 失败处理、费用与结果保存

- 先小样本验证，再运行完整两组；限制并发、单请求超时和重试次数，避免隐式长重试和费用失控。
- 模型请求与裁判请求分别记录成功、失败和已知用量，不能把缺失用量当成免费。
- 失败的生成/评分记录不删除；裁判异常、超时、NaN 等标为不可用，不能当成高分或正常的零分。
- 每项指标同时报告总样本数、有效评分数和失败/不可用数；质量均值有多少题参与必须显式说明。
- 不以删除失败样本或只展示成功题的方式提升分数。
- 不打印凭据，不把包含密钥的配置写入 EvalScope 日志或结果；将模型名、非敏感参数、输入哈希与提示词版本单独持久化。
- 新建生成实验目录，保存原始回答、四字段数据、评分结果、裁判诊断、manifest 和中文总结；禁止覆盖检索实验和旧生成实验。

## 9. 验收条件

1. 数据连接逐题正确，两组各 30 条，保留真实证据及语言；生成提示不包含参考答案。
2. 有离线回归覆盖缺失证据、参考版本漂移、ID 错配、空/截断输出、失败评分和分组统计。
3. 少量真实生成及官方 RAGAS 评分成功，再运行整批；失败或未完成阶段如实披露。
4. 主指标和辅助指标的有效样本数、异常数、中英文分组及两组对照可追溯。
5. 结果明确说明：固定上下文的 RAG 生成评测；B4 未经 JEV 语义校验；参考答案待人工复核；同模型裁判可能有偏；不冒充 Agent 端到端或上线准确率。

## 10. 需要用户确认的默认选择

继续“生成评测”，先固定现有 B3 和无 JEV B4 的检索证据，使用现有千问生成并做首轮裁判；先 4 个回答验证，再扩到 60 个回答及上述五项指标。确认后补充具体实施计划与版本约束，再进入代码实现。
