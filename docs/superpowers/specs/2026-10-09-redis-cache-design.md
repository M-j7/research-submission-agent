## 1. 目标与职责

Redis 负责加速可重建的数据读取和计算，不是记忆原文、知识库原文或任务权威状态的唯一存储。

- 数据库保存权威记录；缓存副本丢失后可以重新读取或计算。
- Agent 调用业务工具，由后台模块管理缓存，不向 Agent 暴露 Redis 管理权限。
- 记忆存储与压缩仍由 MemoryManager 管理，PromptManager 仍只负责组装输入。
- Redis 缓存与模型服务侧的 KV／Prompt Cache 是不同机制。
- 正常空结果、缓存未命中和服务故障必须区分，不能用故障推断“政策不存在”。

第一版最终范围速览：

| 资源 | 权威来源／持久副本 | 加速位置 | 更新方式 |
| --- | --- | --- | --- |
| 用户画像／偏好 | MemoryManager 的 SQL | Redis Hash | 业务更新只写 SQL；缓存 TTL 自然过期 |
| 查询 Embedding | 实际输入及模型配置，可重算 | Redis String | 版本化查询身份＋TTL |
| RAG 检索证据 | 原资料、父子块、Chroma 与检索配置，可重检索 | Redis String | 版本化查询身份＋TTL，不缓存最终答案 |
| 意图示例／模板向量／BM25 索引 | 本地示例文件及派生向量缓存 | 进程内存 | 初始化加载，内容／编码版本变化时重新加载匹配资源 |
| 最新会话与 Agent 执行状态 | MemoryManager／本轮运行时 | 不接入 Redis 读取路径 | 按现有记忆与执行机制管理 |

FAQ、批量活跃用户预热、动态意图得分预热、Stream／PubSub、语义答案缓存、分布式锁及 Redis 集群不在第一版范围。详细合同与预算分别见第 10.5、11、12 节。

## 2. 已选择的基础策略

| 部分 | 设计主线 | 约束 |
| --- | --- | --- |
| 读取模型 | 旁路缓存（Cache Aside） | 先查缓存，未命中再回源，取得有效结果后尝试回填 |
| 业务更新 | 只提交权威数据库，不同步维护普通缓存 | 缓存保留至 TTL 到期或被淘汰；接受短暂旧值 |
| 过期 | TTL 加随机抖动 | 读取命中不自动续期；到期后下一次读取再回源重建 |
| 内存淘汰 | volatile-lru | 只在带 TTL 的键中近似优先淘汰近期较少使用的键 |
| 容量保护 | maxmemory 与单条结果大小限制 | 按部署预算配置；过大结果跳过缓存，不改变业务结果 |
| 穿透保护 | 短 TTL 正常空结果缓存，不引入布隆过滤 | 空结果、未命中与故障分开；只减少相同空查询的重复回源 |
| 击穿保护 | 按缓存键互斥协调重建 | 获取重建权后再次查缓存；等待与计算均有界 |
| 集中过期保护 | 随机 TTL，配合受控重建 | 随机 TTL 不能单独解决 Redis 宕机或单个热点键击穿 |
| Redis 故障 | 短超时、熔断、受控回源 | 只隔离缓存依赖；后端数据库／模型服务仍受预算及并发保护 |
| 缓存预热／初始化加载 | 当前用户已有长期画像进 Redis；固定意图示例与向量进进程内存 | FAQ 及批量活跃用户预热取消；意图分数不预计算，静态资源不默认塞进 prompt |

以上是策略选择，不代表这些能力已经全部实现或验证。

## 3. 内存回收与 TTL

### 3.1 时间过期

TTL 规定缓存何时失效，不保证缓存至少保留到该时刻；内存淘汰可以提前移除缓存。

- 成功写入时设置 TTL，读取命中不自动延长。
- String 的值与 TTL 应通过同一条原子命令设置；Hash／List 的写入与首次设置 TTL 通过事务或脚本成组执行，避免成功创建缓存却遗漏过期时间。读命中不续期，写入时是否重设 TTL 在对象参数中明确。
- 参考贴文采用约 ±10% 随机抖动，例如基础 30 分钟分散为 27～33 分钟。
- TTL 必须保持为正值；具体对象是否有严格最长有效期，需要在参数设计时单独检查，不能让抖动突破硬性上限。
- Redis 自身结合主动检查与访问时检查处理过期键，不额外设计应用清理循环，也不假定所有键到期时会立刻释放物理内存。
- 第一版不默认采用“返回逻辑过期旧值、后台刷新”的策略。

参考贴文的 TTL 候选范围如下，不作为各对象的最终配置：

| 档位 | 候选范围 | 贴文中的用途 |
| --- | --- | --- |
| 短期 | 5～15 分钟 | 工具查询结果、临时派生数据 |
| 中期 | 30 分钟～2 小时 | 会话摘要、画像的缓存副本 |
| 长期 | 6～24 小时 | 变化较少的配置或稳定结果 |

### 3.2 容量淘汰

采用 volatile-lru，并明确设置 maxmemory。

- 淘汰触发于用于淘汰判断的内存达到配置上限，不是 Redis 自动检测整机占用达到某个物理内存比例。
- 物理内存的 60%～70% 只是特定环境的经验参考，不是本项目固定参数。需要考虑 Docker、Chroma、后端及 Redis 额外开销。
- 所有普通结果缓存必须设置 TTL。没有合适的可淘汰键时，相关写入可能因内存不足被拒绝。
- 设置单条结果大小上限，防止一个大结果挤占大量缓存空间。
- 淘汰或过期后按未命中处理。回填失败不撤销已成功获得的业务结果。
- 协调锁不是普通结果缓存，其寿命与淘汰规则需独立设计，不能直接套用上述策略。

## 4. 旁路读取与 TTL 懒更新

读取流程：

```text
查询缓存
├─ 有效命中 → 返回缓存中的业务数据
└─ 未命中／缓存不可用 → 读取数据库或执行计算
                         → 取得有效结果
                         → 尝试回填缓存并设置 TTL
                         → 返回结果
```

更新数据库型数据的流程：

```text
数据库提交成功 → 不主动更新／删除普通缓存
缓存自然过期 → 下次读取回源 → 回填新缓存及 TTL
```

业务更新必须先在权威存储成功提交；缓存不是写入成功的前提。Embedding 等纯计算结果不需要为了缓存额外写入 SQL。

### 一致性边界

第一版允许缓存有效期内读到旧画像、旧结果，不实现主动删除补偿、数据库与 Redis 双写协调或字段级主动更新。

- TTL 从缓存实际写入时计时，不是从数据库更新时计时；慢请求可能晚回填旧快照，不能承诺数据库更新后恰好一个 TTL 内一定读到新值。各次回源仍读取权威来源，不无限续用旧副本。
- 读取命中不续期；预热也不刷新仍有效的旧缓存。设置每类对象 TTL 与回源超时，避免旧快照反复延寿。
- 本地兜底副本不能在 Redis 过期后另起一个更长有效期；需遵循相同的快照寿命。
- 必须读取最新会话输入、当前控制状态或权限时，不依赖 TTL 副本保证正确，使用权威存储／本轮运行时输入。哪些非关键会话视图可容忍陈旧，继续在对象确认时明确。
- 权限、数据撤回及安全边界不能仅靠 TTL；查询仍做鉴权，依法删除／撤回不等同于普通缓存业务更新。

模型及知识库版本仍可作为查询身份的一部分。强一致或即时更新需求未来再单独设计，不将早先讨论的版本校验／主动删除方案视为当前已实现能力。

## 5. 缓存穿透：短 TTL 空结果缓存

用户已选择不引入布隆过滤。成功查询后确实没有结果时，缓存明确的空结果标记，短期内相同查询不重复回源。

- 使用独立的状态，例如 `status=empty`；不能与未命中、读取异常返回的空值混淆。
- 只缓存正常成功的空结果。超时、限流、权限失败、召回失败与降级不属于空结果。
- RAG 空结果表示“此次检索未找到证据”，不等于“政策不存在”；不能仅凭低相关分数宣布不存在。
- 30～60 秒可作为试验起点，尚未确定最终 TTL；同样要求正值及合理抖动。
- 第一版数据新增后，旧空结果也等短 TTL 自然过期；可能短暂读不到刚新增的数据。访问仍需鉴权。
- 限制键数量与容量。大量互不相同的无效查询仍会产生首次回源，需依靠入口校验、限流与并发限制，不声称空缓存能解决所有穿透。

## 6. 缓存击穿：按键协调重建

```text
未命中 → 获取该键的重建权
       → 再次读取缓存
       → 仍未命中才回源重建
       → 回填并释放重建权
```

- 单进程使用异步互斥协调或共享进行中的计算任务；不同缓存键不共用一把全局重建锁。
- 多实例部署需要跨实例协调，本地锁不能保护其他进程。
- 分布式锁需要唯一持有者标记、合理租期、原子校验释放；需要续期时同样校验持有者。
- 未取得重建权的请求有限等待并重新查缓存，不能无限循环，不能随便返回空值误导 Agent。
- 等待者与重建任务需要明确时间预算及取消边界。
- 所有自动重试遵循既定的指数退避、随机抖动、尝试次数和时间限制。
- 协调锁可能失效；它用于减少重复计算，不代替数据库事务、版本校验或幂等保障。

本节互斥针对重建效率，不默认把数据库写入纳入同一把锁，因此不能据此声称缓存读写强一致。

## 7. 雪崩与 Redis 故障

大量缓存集中到期：使用 TTL 抖动，并限制重建并发。

Redis 不可用：

```text
缓存短超时／失败
→ 持续故障时熔断缓存调用
→ 绕过 Redis，受控访问数据库或计算服务
→ 冷却后少量探测
→ 恢复后重新允许缓存读写
```

- “回源”是绕过缓存获取业务结果，不等于不等待结果、把业务请求全部异步丢到后台。
- 熔断 Redis，不是关闭整个 Agent 或数据库。
- 不能让每个请求继续对故障 Redis 进行长时间等待或层层重试。
- 回源仍受并发、队列容量、时间、重试和服务预算约束；过载时明确拒绝或降级，不能承诺无限吞吐。
- 本地 Redis 协调能力失效时，不能假装仍有跨实例互斥；结果缓存可以受控降级，关键写入仍依赖权威存储的正确性机制。

具体超时、熔断阈值、探测数量、等待上限和容量参数尚未冻结。

## 8. 缓存预热

FAQ 预热已取消，后续又取消批量活跃用户方案。Redis 只提前加载当前合法用户的已有长期画像；固定意图示例／向量在应用初始化时加载进本地进程内存。具体简化方案见第 12 节，不代表全部实现。

### 8.1 预热内容建议

- 用户画像：只加载当前用户现有画像与偏好，不扫描所有用户、不加载完整历史，不为了预热临时提取新画像。字段遵循最小必要原则，按用户身份隔离。
- 不另建标准问答库，也不增加绕过 Agent 直接返回缓存答案的入口。RAG 缓存仅存检索证据。

### 8.2 执行与保护建议

- 当前用户身份绑定后提前加载该用户画像，不阻塞其他初始化工作；Redis 恢复后按正常请求回源回填，不安排批量补热任务。知识库换版不触发无关的画像预热。
- 先检查有效命中，再加载缺项；复用正常缓存键、权限作用域、数据校验、TTL 抖动和按键协调重建，避免多实例重复预热同一批数据。
- 当前用户只加载一份画像，沿用画像读取预算及缓存大小限制；不另设 Top 100／Top 1000 或活跃 5000 用户批次。
- Redis 或回源服务故障时停止／跳过预热；自动重试仍遵循既定的次数、时间、退避与抖动限制。
- 画像更新提交数据库后不主动维护缓存；预热只补缺项，不刷新有效命中，遵循第 4 节的陈旧读取边界。

预热只是提前执行原本在首次访问时发生的加载，不改变权威数据源，也不延长数据的业务有效期。

## 9. 缓存对象与键规范：讨论稿

本节根据用户截图提出方案，供下一轮确认；不把候选对象和参数当成已批准的实现规格。

### 9.1 键命名建议

采用截图的五段结构：

```text
{业务名}:{数据类别}:{实体}:{标识}:{结构版本}
submission:cache:profile:u_123:v1
submission:cache:session_meta:u_123_c_456:v1
submission:cache:session_turns:u_123_c_456:v1
submission:cache:embedding:<指纹>:v1
submission:cache:rag:<指纹>:v1
```

- 大括号只是格式占位符，不照抄为 Redis Cluster 的 hash tag。`cache` 是业务数据类别，不是 Redis 的 String／Hash 类型。
- 环境之间使用独立部署或不同业务前缀，如 `submission_dev`；标识使用内部稳定 ID，不用姓名、邮箱或原始问题。
- 指纹来自字段顺序稳定的序列化输入，建议采用 SHA-256；避免用不稳定的进程内 hash。哈希不能替代加密或鉴权。
- `v1` 表示缓存数据结构版本，不是知识库内容版本。模型、知识库、规则及检索配置等影响结果的版本纳入指纹，并在值中保留用于验证。
- 用户级缓存按用户隔离，会话级缓存同时绑定用户与会话；公开知识缓存只有在内容和访问范围确实公共时才跨用户复用。
- 不做会改变语义的激进归一化，不丢失否定词、期刊、年份或数字。带历史指代的查询先明确语义，或者将必要背景纳入键身份。
- 键长度以可读且适度为目标，不将文章的 50 字符当作 Redis 硬限制。不要将 request_id 放入普通复用键；命中标记、耗时等请求级字段由当前请求生成。

### 9.2 缓存对象建议

| 对象 | 建议缓存内容 | 命中身份／更新边界 | 预热建议 |
| --- | --- | --- | --- |
| 用户画像 | 当前有效画像、偏好、画像版本和来源引用；不是完整历史原文 | 用户与权限作用域；TTL 自然过期，更新后可能暂时读旧偏好 | 当前合法用户 |
| 公共短期记忆读取视图 | 本会话旧摘要＋最近五轮完整问答、必要会话事实及记录引用 | 用户＋会话；若缓存则容忍 TTL 内旧视图；需要最新五轮或本轮模式时读取权威来源，不用旧视图替代 | 首次访问按需加载，实际启用范围继续确认 |
| 查询 Embedding | 查询向量、维度、模型标识 | 实际输入文本＋模型版本＋编码配置；不复制全部 Chroma 文档向量 | 热点查询按需，暂不单独批量预热 |
| RAG 检索结果 | 证据正文、父子块 ID、来源／定位、排序分数、检索版本；不缓存请求级调用 ID | 有效查询＋top_k＋过滤／权限范围＋知识库／改写／术语／融合／reranker 配置版本；有故障或不完整降级不作正常结果复用 | 按需加载 |

用户进一步选择按对象使用不同结构：画像／偏好与会话状态使用 Hash，最近 N 轮问答使用 List，可复用的只读工具结果使用 String＋TTL，替代早先统一 String 的建议。具体字段及更新协议见第 9.4 节，仍需审核。

当前公共字段及类型以第 10.5 节具体合同为准，包含结构、业务状态、作用域、版本及缓存寿命信息。明确空结果使用相同键身份和不同状态，真实 TTL 由 Redis 设置，不靠 JSON 时间字段自行保证过期。

### 9.3 暂不纳入

完整记忆原文、知识库全量原文和索引、Agent 私有执行轨迹、权威任务状态不迁入 Redis。Skill／固定模板优先本地复用；任意最终回答、完整计划、语义答案缓存及其他工具结果不默认加入。RAG 本身是工具，不另设一层重复的通用工具缓存。

### 9.4 Hash／List／String 字段与更新建议

本节记录用户选择的结构，字段为针对本项目的建议，不增加运行时代码。

| 缓存 | 结构 | 字段／元素建议 |
| --- | --- | --- |
| 用户画像与偏好 | Hash，`profile` 键 | 沿用 MemoryManager 字段：`language`、`response_style`、`citation_preference`、`research_direction`、`writing_language`、`submission_experience`、`ongoing_requirement`；元数据见第 10.5 节 |
| 会话状态读取视图 | Hash，`session_meta` 键 | `current_mode`、`target_journal`、`submission_stage`、`older_summary`、`summary_revision`、`summary_source_refs`、`conversation_revision`、`updated_at`、`schema_version` |
| 最近五轮完整问答 | List，`session_turns` 键 | 每项一个 JSON 问答对象：`turn_id`、`seq`、`user_message`、`assistant_message`、`source_refs`、`created_at`、`schema_version` |
| RAG 等可复用只读工具结果 | String＋TTL | 第 10.5 节 JSON 外壳及证据 schema；RAG 保存证据与定位，不保存通用最终回答 |
| 查询向量 | String＋TTL | 向量、维度、模型及编码配置版本，具体合同见第 10.5 节 |

画像字段只保存用户确认或带合法来源的值，不填猜测值。稳定偏好放用户级 Hash；当前模式、当前期刊和阶段放会话级 Hash，不把会话变化自动提升为长期画像。多值字段与来源列表以 JSON 编码；读取后统一做 schema 校验。

会话 Hash 不是 Agent 私有状态栏或正在执行的任务锁；这些内容继续由原有瞬时记忆／运行时管理。若当前模式尚无持久来源，必须先确定权威存储，不让 Redis 成为唯一状态源。

**更新协议：**

1. 用户最新决定采用 TTL 懒更新：业务仅提交数据库，不主动改／删缓存；缓存缺失或到期后，读取数据库快照重建并设置 TTL。
2. Hash 在重建时用 HSET 发布完整字段，第一版不在每次业务更新后做字段级增量回填。Hash 的字段操作能力不等于自动一致性。
3. 不再把主动删除补偿作为第一版实现项。字段版本供数据识别，不声称自动防止旧值；本地兜底同样遵守 TTL，不延长副本寿命。

**最近问答 List：**

- 一项是一整轮“用户问题＋最终助手答案”，不是一条消息，也不是一次工具调用。多 Agent 中间答案不作为多轮公开问答塞入该 List。
- `LPUSH` 放入最新项，`LTRIM key 0 4` 保留最新五项；新项在左侧，组装 prompt 时转为从旧到新的顺序。List 本身不会自动封顶，必须执行 LTRIM；条数封顶也不等于字节／token 封顶，仍需大小限制。
- 第一版不每轮增量维护 List，缓存缺失时从 SQL 取最近五轮，成组发布完整窗口并设置 TTL。LPUSH／LTRIM 可用于构建有界列表，但不作为每轮业务提交的强制附加写入；不能因操作重试重复追加。实时对话 prompt 所需的最新问答不依赖陈旧 List。
- LTRIM 只移除缓存中的旧项，不删除 SQL 原文。旧轮摘要由 MemoryManager 生成并持久保存，不由 Redis 截断动作生成。
- 会话 Hash 与 List 分开后，组装时要检查窗口与会话版本是否相配；缺一份、窗口不完整或版本不匹配时，从同一个 SQL 快照重建所需视图，不拼接不同时点的数据。

**工具与故障边界：**

- 只缓存白名单内可复用的只读查询结果，键指纹包含工具名称／版本、参数、权限范围及数据／配置版本。RAG 继续使用自己的结果缓存，不叠加另一份通用工具缓存。
- 提交、删除、写文件等有副作用工具不靠结果缓存跳过执行；其重复执行控制属于幂等设计。正常空结果用短 TTL，超时／权限失败／降级不写成正常命中。
- Redis 故障时，画像／会话回 SQL，RAG 回检索后端，外部只读工具回对应服务；不是所有工具结果都能从 SQL 获取。短超时与熔断避免持续等待，回源限流／并发保护避免后端过载。
- 缓存写失败不回滚已经提交的 SQL，也不要求重新执行业务副作用。只有权威存储成功且所需结果可获取时，才能返回业务成功；不能将降级描述为所有故障都不影响业务。

## 10. 第一版收敛方案：已确认基线

用户已确认收敛方案与 TTL 试验起点，随后取消 FAQ。它沿用 TTL 懒更新原则，不代表运行时已落地；具体字段／权限／版本设计见第 10.5 节，已确认运行参数见第 11 节，简化提前加载见第 12 节。第 9 节保留未启用的会话结构供参考，实际第一版启用范围以本节为准。

### 10.1 优先范围

- 第一版启用用户画像 Hash，以及 RAG 结果、查询 Embedding 的 String 缓存。提前加载当前用户画像，FAQ 缓存／预热取消；固定意图资源另在进程内加载，不扩展 Redis 业务对象。
- 会话 Hash／最近五轮 List 保留结构设计，第一版暂不启用该缓存读取路径，也不接入实时 prompt。最新问答、当前模式及私有瞬时执行信息继续从 MemoryManager／本轮运行时取得，避免用户上一轮的信息在 TTL 内不可见。
- 非实时会话读取视图若以后需要加速，再确认可容忍的陈旧程度；不为展示 Hash／List 而增加一条无实际收益的在线路径。

### 10.2 一条统一缓存路径

```text
确定完整输入与权限范围 → 生成缓存键 → 有效命中则复用
                                   → 未命中则按键协调
                                      → 再查缓存
                                      → 有界回源
                                      → 校验结果
                                      → 尝试缓存并返回
```

缓存未命中与正常空结果不同，故障与降级不伪装为正常命中。调用 ID、请求耗时及命中标记由当前请求生成，不能复用历史调用元数据。业务更新只提交权威来源，缓存按 TTL 自然过期。

缓存访问层由后台管理，Agent 不直接操作 Redis。第一版不再额外加入 Stream、Pub/Sub、布隆过滤、语义答案缓存或分布式字段更新。

### 10.3 参数试验起点

下表是用户已确认的基础 TTL 试验起点，不是实测最优值；加约 ±10% 抖动，命中不续期。后续依据实际效果调整，不将同意试验参数描述为性能验收通过。

| 对象 | 基础 TTL 建议 | 原因／条件 |
| --- | --- | --- |
| 用户画像 | 5 分钟 | TTL-only 下缩短旧偏好的存活时间；本轮明确的新指令优先，不被旧画像覆盖 |
| RAG 检索结果 | 10 分钟 | 复用短时间内重复检索，键绑定知识库与完整检索配置版本 |
| 查询 Embedding | 24 小时 | 相同输入及模型编码配置可复用，不受会话状态更新影响 |
| 正常空结果 | 30 秒 | 减少相同空查询的回源，限制新增数据暂不可见时间 |

回源时间仍需限制；TTL 计时起点及迟到回填边界见第 4 节。不将过期抖动当成严格最长陈旧时间保障。

### 10.4 实现前剩余必需项

1. 审核第 10.5 节的字段 schema、键指纹输入与权限范围，后续按合同实现；落实知识库／模型换版时如何切换实际版本。
2. 按第 12 节实现简化提前加载，复用既定预算，确认意图向量缺失时的受控构建／未就绪处理；不重启已取消的 FAQ 或批量活跃用户工作。
3. 确定连接池、调用超时、按键等待与回源上限，以及 Redis 熔断／半开恢复参数；单进程先用本地异步协调，多实例再设计分布式锁，避免锁被普通缓存淘汰。
4. 配置部署内存预算、volatile-lru、单条大小与键数量限制；Redis 不对公网暴露，配置访问控制。本地兜底如保留，必须有容量和寿命约束，不扩展为复杂的多级一致性系统。
5. 验收有效／空／未命中区分、同键并发、TTL 过期、坏缓存、Redis 故障与恢复，以及用户隔离和最新会话读取。日志与监测最后统一设计，不提前声称性能提升。

当前代码仅有基础 RAG 缓存、固定 TTL、可选 Redis／本地兜底与进程内锁；本节的结构、抖动、预热、熔断等并未因文档更新而自动实现。

### 10.5 缓存数据合同：schema、权限与版本

以下是本次具体设计，尚未转换成运行时 Pydantic 模型。实施时沿用项目的严格校验风格：拒绝未知字段、错误类型、无效版本和超限值；不执行缓存内的脚本或反序列化 pickle。

#### A. 统一读取状态

缓存访问层返回带标签的读取结果，不用一个 `None` 表示所有情况：

| 读取状态 | 含义 | 后续处理 |
| --- | --- | --- |
| `hit` | 有效缓存；其中业务状态还分 `ok`／`empty` | 按缓存的正常业务结果返回 |
| `miss` | 键不存在、过期或被淘汰 | 有界回源 |
| `invalid` | JSON／字段／作用域／配置版本不匹配，或快照已过期 | 不使用该值，有界回源；不伪装成业务空结果 |
| `unavailable` | Redis 超时／断连／熔断等 | 受控回源；仅允许使用仍有效且同权限的本地副本 |

只有 `hit` 携带业务数据。`empty` 是正常成功查询的结果，不是缓存读取状态，也不是故障。运行时可映射到现有 ToolResult 的 `ok`／`empty`；其 `partial`／`error` 不作为第一版可复用缓存写入。

#### B. 权限来源与命中身份

- 第一版三个缓存域统一按用户隔离，`owner_id` 从已绑定的 Request／认证上下文取得，不允许模型或工具参数任意传入另一个 user_id。入口身份绑定／认证仍由入口负责，缓存不承担认证。
- 画像可供同一用户的多个会话复用；只读已授权用户的画像，不能读取其他 Agent 的私有执行记录。
- 查询向量与 RAG 即使使用公开 IEEE 文档，也先按用户隔离，避免带个人背景的查询跨用户复用。跨用户公共查询缓存暂不启用。
- `access_scope` 由后端定义，表示可见资源范围；目前 RAG 的官方资料范围为 `official-ieee`。用户仍须通过当前访问检查，不凭缓存中的 scope 获得权限。
- 向量与 RAG 键指纹均包含 `owner_id`、`access_scope`、实际输入及相关版本；RAG 再包含 top_k 与全部过滤条件。同名模型用于不同提供方／编码设置时，不能共享错误向量。
- 画像键继续使用稳定的内部用户 ID。值中的 `profile_revision` 表示被缓存的快照版本；TTL-only 不每次去 SQL 查询当前 revision，也不声称画像永远最新。
- 所有版本字段来自后台实际资源／配置，不让 LLM 编造。模型／索引配置未知、已切换但尚未加载或无法取得匹配版本时，不复用旧缓存。版本变化需要刷新运行时实际配置，不能只改显示字符串。

#### C. 用户画像 Hash

键：`submission:cache:profile:<内部用户标识>:v1`。

元数据 field：

| field | 解码后的类型／约束 |
| --- | --- |
| `_schema_version` | 整数，固定 1 |
| `_kind` | 固定 `profile` |
| `_status` | `ok` 或 `empty` |
| `_owner_id` | 当前请求绑定的非空用户 ID |
| `_access_scope` | 固定 `user-profile` |
| `_profile_revision` | SQL 用户画像快照版本，非负整数 |
| `_cached_at`、`_expires_at` | UTC 时间，后者晚于前者；供快照寿命核对 |

业务 field 白名单沿用现有 MemoryManager：`language`、`response_style`、`citation_preference`、`research_direction`、`writing_language`、`submission_experience`、`ongoing_requirement`。

每个业务 field 的值为 JSON：`{record_id, value, source_refs, revision}`。record_id 是画像记录 ID，source_refs 是非空原文 ID 列表，revision 是该记录的正整数版本；value 沿用 SQL 的有界 JSON 值，不在缓存层重新推断画像。只包含 `state=active` 的项，不补不存在的字段，存在冲突／撤回的项不直接写成当前有效事实。

- `ok` 必须至少有一项有效画像；`empty` 没有业务 field，表示成功读取后没有有效画像，不等于用户未认证／不存在或 SQL 失败。
- 普通画像 TTL 为 5 分钟；正常空画像采用空结果 TTL 30 秒，均加抖动。
- Redis Hash field 实际存字符串，读取后严格解码；业务字段名与 `_` 元数据命名空间分离。重建发布整份快照与 TTL，避免半份画像或旧字段残留；不在 SQL 更新时做主动字段修改。

#### D. String 缓存公共外壳

Embedding 与 RAG 使用 JSON 外壳：

```text
schema_version: 1
kind: embedding | rag
status: ok | empty
scope: {owner_id: string, access_scope: string}
versions: 按 kind 定义的版本对象
cached_at: UTC 时间
expires_at: UTC 时间
data: 按 kind 定义的业务对象
```

`scope`、版本及 kind 必须与调用方期待值相符，不能只因 key 存在就返回。Redis TTL 是实际过期机制；外壳时间仅帮助验证快照及约束本地副本，不替代 Redis EXPIRE。外壳不保存原始用户问题、请求 ID、tool_call_id、历史耗时、缓存命中标记或密钥。

#### E. 查询 Embedding String

键：`submission:cache:embedding:<SHA-256指纹>:v1`。

- `versions`：`model_id: string`、`embedding_config_version: string`，均非空。配置版本覆盖提供方、模型修订（可取得时）、维度、编码指令、预处理及归一化设置；不把 API 密钥写入版本或缓存。
- 第一版 `scope.access_scope` 固定为后端的 `user-query`，并绑定 owner_id；不从模型输出接受自定义范围。
- `data`：`vector: list[float]`、`dimension: int > 0`。向量非空，只允许有限数值，不允许 NaN／Infinity；维度与列表长度及调用方模型配置一致。
- 指纹输入：用户身份、访问范围、真正传给模型的文本、模型／编码配置版本。保留否定词、数字和必要背景，不为提高命中率而随意删词。
- TTL 为 24 小时加抖动。只接受 `status=ok`；Embedding 空向量不是正常空结果，校验失败／API 失败不写缓存。

#### F. RAG 检索结果 String

键：`submission:cache:rag:<SHA-256指纹>:v1`。

- `versions`：`knowledge_version: string`、`retrieval_config_version: string`，均非空。知识版本覆盖父子块／索引内容；检索配置版本覆盖实际 Embedding、BM25、术语表、Multi-Query／JEV、RRF、reranker 与父块扩展设置。
- 指纹输入：用户身份、访问范围、已明确语义的原查询、top_k、过滤条件和上述版本。若查询仍依赖会话背景，先明确语义或把必要背景纳入身份，不能只用“那这个呢”命中别的上下文。
- `data`：`{evidence: list[Evidence]}`。不缓存最终助手回答；展示时的调用 ID、命中标记与请求耗时由当前请求生成。
- Evidence 必需字段：`evidence_id: string`、`parent_chunk_id: string`、`matched_child_id: string`、`text: string`，均非空；`title: string|null`、`source_url: string|null`、`source_locator: string|int|null`、`source_version: string|null`、`collected_at: UTC时间|null`、`resource_ref: string|null`、`ranking_scores: {rrf: finite_float, rerank: finite_float|null}`。
- 来源字段沿用检索实际元数据，不编造 URL／定位；source_url 或可访问的 resource_ref 至少提供一个可追溯入口，否则不把该结果写成合格缓存。资源引用只能指向当前授权范围，分数不是正确概率。
- `ok` 要求证据非空，数量不超过该调用 top_k（当前入口范围 1～10）；TTL 为 10 分钟加抖动。`empty` 要求证据为空且所有启用的必要检索步骤正常完成，TTL 为 30 秒加抖动；表达“本次未检索到证据”，不推断政策不存在。
- 有召回路径失败、改写／校验故障、reranker 降级、错误或警告的结果可供当前请求明确降级使用，但第一版不写成正常可复用缓存。

#### G. 验证边界

后续必须测试：命中空结果不重复回源，miss 会回源，故障不转 empty，Embedding 无效向量不落缓存，不同用户／top_k／过滤范围／模型／知识版本不能串结果，画像来源及 active 状态正确，未知字段与坏 JSON 不被直接拼进 prompt。这些是验收要求，不是已运行通过的测试。

## 11. Redis 运行参数：已确认试验基线

用户已确认本节作为第一版运行参数基线。它是待实现、待验证的试验默认值，不是压测结论或生产 SLA。假设应用主要在单机／本地 Docker 上以单进程运行，Redis 为可选加速层；多实例部署需要重新校准总体并发及协调方式。

### 11.1 选择理由

推荐快速绕过缓存故障、有界共享计算的方案。另一种方案是在请求内反复重试 Redis，适合必须依赖 Redis 的业务，但本项目可回源，会增加故障时延；增加完整多级缓存是第三种方案，可进一步减少网络调用，但会增加容量和副本寿命管理，本轮不扩展。

### 11.2 Redis 连接与操作

| 参数 | 建议默认值 | 原因／边界 |
| --- | --- | --- |
| 每进程连接池上限 | 16 | Redis 调用短，连接不需要跟随 Agent／模型任务一一增长；先限制资源，不照搬文章的 50 |
| 建连超时 | 300 ms | 本机网络应较快，连接失败尽快回源；远程部署需重新测量 |
| socket 超时 | 300 ms | 避免读写挂起，约束实际网络等待 |
| 单次缓存访问总预算 | 500 ms | 包含获取连接、建立连接与命令执行，不把各层超时相加；沿用现有外层 0.5 秒起点 |
| 请求内 Redis 自动重试 | 0 次（仅初次尝试） | 缓存可跳过，不为了加速层增加指数重试链；SDK 隐式重试也应关闭 |

- 连接池按进程初始化并复用，服务结束时关闭；不为每次工具调用新建客户端。
- 池满时快速绕过，不另排一个无限连接队列；这是本地资源饱和，不当作 Redis 网络失败触发熔断。
- 一次 Redis 故障后，该次缓存加载流程不继续尝试故障 Redis 的二次查询／回填；下一次独立访问或半开探测再判断可用性。
- 缓存写入同样有 500 ms 总预算，失败／超时跳过；已经得到的正常业务结果不变。
- 500 ms 是一次访问的上限，不宣称整个请求只付出一次 500 ms。健康时的首次读取、协调后的复查和结果回填可以是不同访问，均服从业务剩余时间。
- 若以后增加自动重试，统一沿用指数退避、随机抖动、次数和时间上限。第一版没有请求内 Redis 重试，不设置一套相互嵌套的重试参数。

### 11.3 按键共享任务与回源保护

使用单进程按完整缓存键共享进行中的任务（single-flight）；已有任务时加入等待，不重复回源。任务取得执行权后再次读缓存。它替代单纯“各请求轮流持有锁再调用 loader”的等待行为。

| 回源类型 | 每进程执行并发 | 排队上限 | 一次加载的总时间上限 |
| --- | --- | --- | --- |
| 用户画像 SQL 读取 | 4 | 8 个不同 key | 2 秒 |
| 查询 Embedding | 4 | 8 个不同 key | 30 秒 |
| 完整 RAG 管线 | 2 | 8 个不同 key | 90 秒 |

- 一个 key 的等待者最多 16 个；超过返回明确的繁忙状态，不能创建另一个同 key 计算。不同 key 排队超过上限也返回繁忙，不绕过限流继续回源。
- 表中排队按不同计算任务计数，不将同 key 等待者当成额外回源任务。并发保护覆盖正常未命中、Redis 故障与预热，不能在降级时绕过。
- 等待者自己的总预算从首次进入该加载流程计时，包含排队、共享任务等待及缓存访问；不能排队 90 秒后再重新获得 90 秒计算时间。到期返回超时／未完成，不缓存成 empty，也不再发起同 key 重复查询。
- 共享任务也有从创建时开始的总上限。有效截止时间取本类型上限、Agent／工具剩余时间及现有更短子调用预算的最小值；现有 RAG 子 HTTP 请求 30 秒限制保留。
- RAG 的 90 秒沿用当前管线及工具调用上限，不强制把昂贵检索塞进 Redis 的 500 ms。直接 Embedding 与 RAG 内部的 Embedding 都经过同一提供方调用限制，最多 4 个在途请求；完整 RAG 限 2 并不代表最多只有 2 个子 API 请求。
- SQL 的 2 秒是拟采用的加载预算，不宣称当前 SQLite 的 `timeout=5` 能实现它。SQLite timeout 主要限制锁等待；实施时要避免同步数据库读取阻塞事件循环，并落实原生超时／安全取消边界。外层 wait_for 不保证后台 SQL 或远端模型实际已停止。
- 取消一个等待者不取消仍被其他等待者使用的任务；无人等待或共享任务到期时尽力取消。任务完成／失败后清理注册项，不能无限累积锁／Future。
- 第一版没有 Redis 分布式锁，也不声称保护其他进程；后续多进程时每进程参数会累加，必须重设全局配额并设计跨实例协调。

### 11.4 Redis 专用熔断器

```text
正常（允许缓存调用）
  → 30 秒内连续 5 次连接／网络超时失败
  → 熔断（15 秒内跳过 Redis，受控回源）
  → 半开（仅 1 个探测任务，其余请求继续绕过）
     ├─ 成功 → 恢复，清零失败计数
     └─ 失败 → 再熔断 15 秒
```

- 同一进程共用一个 Redis 网络依赖熔断状态；并发计数及半开名额更新需要原子保护。
- 连续失败计数在成功网络调用后重置，超过 30 秒的旧失败不累计。计数依据实际 Redis 调用，不依据共享任务等待者数量。
- 正常未命中、业务 empty、应用 schema 错误、RAG／数据库故障和本地池满，不计作 Redis 网络失败。OOM 等写容量问题跳过回填，不把仍可读取的 Redis 宣告网络失联。
- 认证／ACL／配置错误不按瞬时网络故障反复探测；停用对应不可用缓存能力，配置修正后重新初始化。缓存降级不等于权限检查降级。
- 半开探测使用后台生成的专用无敏感信息探测键，写入短 TTL 值并读回核验，整体仍限 500 ms；确认基本网络及 String 读写，不声称验证了 Hash 的全部 ACL／命令能力。Hash 权限在初始化／实际访问时单独校验；单独 PING 成功不等于业务读写全部恢复。
- 熔断持续期间不在每个请求里 sleep／重试，不熔断 SQL、模型或整个 Agent。状态切换依据单调时钟与依赖代次，迟到的旧请求结果不能覆盖新半开／熔断状态。
- 5 次、30 秒及 15 秒均为试验默认值，后续根据误触发与故障恢复情况调整；没有当前性能数字作为生产保证。

### 11.5 预算、验收与未决项

## 12. 简化预热与固定意图资源加载：已确认范围

用户确认“意图识别的”指示例库和示例向量，不是用户问题的意图结果。取消上一稿的最近 24 小时活跃用户筛选、100 用户批次、批量字节预算及恢复补热定时器；只做下面两类提前加载。本次仍不写运行时代码、不触发网络模型调用。

| 内容 | 来源 → 目标 | 时机 |
| --- | --- | --- |
| 当前用户已有长期画像／偏好 | MemoryManager／SQL → Redis Hash | 当前用户身份绑定后，首次使用前尽量提前加载 |
| 固定意图示例库、示例向量及 BM25 索引 | 内置示例文件／已计算的向量缓存 → 进程内存 | 应用／识别器初始化时加载，每进程复用 |

### 12.1 长期画像提前加载

- 仅加载当前合法用户有效画像及来源／版本，不传完整历史原文，不为了预热生成、压缩或修改长期记忆。
- 复用第 10.5 节画像 schema、第 11 节 2 秒读取预算与同 key 共享加载。每个用户同一轮准备不重复发起加载；正常请求先需要该画像时加入已有任务。
- 有效缓存已存在则跳过，不续期；不存在时读取 SQL，校验后发布 Hash＋5 分钟 TTL 抖动，成功查到空画像则使用既定短 TTL。
- Redis 故障时不强制完成预热，真正业务读取仍可受控回源。初始化中的后台加载需在关闭前收束，取消预热等待者不误取消前台共用任务。
- 长期画像是可复用数据，真正使用时仍由 PromptManager 组装；提前加载不等于将所有记忆一股脑写入每个 Agent 的 prompt。

### 12.2 意图静态资源加载

- 示例库包括业务意图及非业务示例，维持意图 ID、示例文本与向量的一一映射；BM25 索引从同一版示例构建并在进程内复用。
- 优先复用已有示例向量的磁盘缓存，不在每次启动重新计算。加载校验示例内容／顺序指纹、模型／提供方／编码配置版本、向量数量、维度及有限数值；维度相同不意味着不同模型的向量可混用。
- 示例更新或模型／编码配置改变时，使用匹配的新资源版本；一次识别使用一组一致的示例／BM25／向量快照，不混入两版资源。
- 预先计算的是固定示例向量。用户输入的查询向量和 JEV／Embedding／BM25 意图分数仍在收到真实请求后产生，不把动态意图分数当作静态预热数据。
- 静态意图资源不必搬进 Redis，也不因 Redis 宕机丢失；示例文件及派生向量缓存保留本地持久副本，进程重启可重新加载。
- 向量缓存缺失／无效时不能静默复用旧版。受预算控制的构建可沿用已有在线模式，但不得在未允许联网／付费的模式里偷偷生成；构建失败明确标记该分支未就绪，按既定识别失败／降级规则处理，不伪造得分。当前设计记录不触发构建。

### 12.3 现有能力与验收

代码核对：BM25 识别器目前在构造时加载示例并建立索引；Embedding 识别器已有模板向量指纹、磁盘缓存和进程内复用，但向量准备是在识别调用时按需触发。将向量准备前移到初始化是后续实现项，不能因文档确认便宣称已完成。

后续验收覆盖：同用户不重复加载、画像 TTL 不续期、示例／向量对应关系及配置版本正确、已有向量不重复计算、未授权模式不产生 API 调用、缺失分支不伪造分数，以及资源关闭／异常降级。本次未运行这些测试。

## 13. 部署容量与安全配置：建议默认值

本节给出本地／Docker 单实例的实现起点，不是对当前机器剩余资源的实测配置，也不执行部署。应用只依赖 Redis 做加速，第一版不搭主从、哨兵或集群；以后可用性和容量确有要求时再升级部署。

### 13.1 部署与生命周期

- 独立的项目缓存 Redis，不与 EchoMind 或其他项目共用同一实例／管理权限。开发可沿用参考文章的 Redis 7.2 兼容线，部署前固定实际镜像版本／摘要并验证 redis-py；不使用 latest，也不声称此兼容线是当前最新版本。
- 后端在 Windows 宿主机运行时，仅发布到 `127.0.0.1:<可配置端口>`；默认候选端口为 6379，冲突时改项目端口，不能停止或覆盖其他已有服务。后端同在 Compose 时走独立内部网络，不必对宿主机发布 Redis 端口。
- 新建纯缓存实例建议 `appendonly no` 且禁用 RDB 定时保存；缓存重启后丢失可回源重建，不为缓存额外引入磁盘恢复与画像落盘副本。此设置不用于已有数据库，也不清理任何既有文件／卷。
- SQL 记忆原文、知识库及本地意图示例／向量副本按原存储方式独立保留，不能因关闭 Redis 持久化而关闭它们的持久化。
- Redis 可自动重启，但应用不把 Redis 健康作为唯一就绪前提；缓存失效时允许明确的降级状态。权威 SQL 或必要输入配置不可用时不得假装业务正常。
- 关闭顺序：停止接收新加载，收束后台／共享任务，再关闭 Redis 连接池及 MemoryManager。应用不因缓存组件停用而重复执行已提交业务。

### 13.2 内存与对象上限

| 项目 | 建议默认值 | 原因／处理 |
| --- | --- | --- |
| Redis maxmemory | 256 MiB | 只存三类结果缓存，先用有限预算；不占整机内存的固定比例 |
| Redis 容器内存上限 | 512 MiB | 与 maxmemory 分开，为进程、连接、分配器及瞬时开销留余量；仍需上线前测量峰值 |
| 淘汰 | volatile-lru | 沿用用户选择，普通缓存和探测键都带 TTL |
| Redis maxclients | 128 | 单进程应用连接池 16，留健康检查／管理连接余量；不是应用并发上限 |
| 单份画像序列化上限 | 64 KiB | 有限画像字段与来源引用，超限不截断事实，只跳过缓存 |
| 单份查询向量 JSON 上限 | 128 KiB | 容纳正常向量及元数据，超限仍返回有效向量但不缓存 |
| 单份 RAG JSON 上限 | 256 KiB | 限制父块正文重复膨胀，超限仍返回业务允许范围内的证据，不偷偷截断答案依据 |
| 本地结果兜底（如保留） | 每进程最多 128 条且序列化内容合计 8 MiB | 同时限制条数与字节，按 LRU 淘汰；这不是整个 Python 进程 RSS 的上限 |

- 普通缓存 key 必须带 TTL，Hash 快照发布与 TTL 成组完成。volatile-lru 没有可淘汰键时会拒绝部分写入，不能假定它能淘汰任何数据。
- 对 Redis 第一版不加复杂的精确全局 key 计数器；高基数由输入校验、有限回源并发、TTL、对象大小和 maxmemory 共同约束。本地结果与共享任务登记必须各自有界，拒绝容量超限，而不是无限新增。
- 单条大小按实际序列化 UTF-8 字节检查；Redis Hash 内部结构、客户端对象及 Python 解码对象仍有额外内存开销，不拿序列化大小冒充实际 RAM。
- maxmemory 与容器内存限制都不是物理内存 60%～70% 的自动阈值。若主机／Docker 预算不足，实施前下调；若内存压力影响正常查询，先检查缓存收益与对象大小，再扩容。
- 最终禁止本地副本延长寿命：复制时只继承原快照剩余有效期，不能每次命中又给本地副本新增一个完整 TTL；本地命中仍校验 scope／配置版本。
- 共享任务登记项与同 key 等待者继续受第 11 节队列、等待者及时间上限约束，任务退出即清理，不用 Redis TTL 替代本地生命周期管理。

### 13.3 网络、身份与命令权限

- Redis 不开放到公网，保留 protected-mode；同项目专用网络也不等于用户级鉴权。远程跨机／不可信网络使用 TLS 和受限网络入口，本地受控开发网络可使用普通连接。
- 使用独立应用 ACL 用户，关闭或限制无认证默认用户；凭证由本地受保护配置／容器 secret 注入，不写进示例 key、源码、Markdown、工具结果或日志。不得打印含密码的 REDIS_URL。
- 应用用户仅能访问项目缓存前缀，例如 `submission:cache:*`；开发／测试前缀与实例独立。应用不应取得其他项目 key 或 Redis 管理权限。
- 业务命令白名单以 GET、SET、HGETALL、HSET、EXPIRE、TTL／PTTL、DEL／UNLINK 与必要事务命令为基础；连接协商需要的安全命令按实际 SDK 验证。后台管理 ACL、配置、FLUSHALL／FLUSHDB 等能力不授予 Agent 或普通应用用户。
- Hash 重建可在事务里替换整份旧快照再设置 TTL；这属于加载回填写入，不是数据库更新时主动失效的另一套策略。事务不能保证 SQL 与 Redis 原子提交，也不自动保证旧值不会回填。
- 第一版应用不使用 KEYS 或热路径全库 SCAN，也不依赖它们维持容量；管理人员确需检查时使用独立受控身份及有界操作。
- Redis ACL 限制的是应用服务权限，不会自动区分同一服务内的终端用户。用户隔离仍由可信 Request、key 身份和返回值 scope 检查共同实现。
- 返回的缓存内容一律视为待验证数据；schema 正确不代表正文可信，RAG 文档中嵌入的指令不升级为系统指令，资源 URL／引用不能借缓存越过工具访问边界。
- 权限收回、用户数据删除与安全事件不适用“等 TTL 就行”的业务懒更新。应立即阻止访问并按安全／数据删除流程清理派生副本；如果不能保证清理，停用对应缓存读取能力，不继续提供旧敏感数据。

### 13.4 配置职责

缓存配置集中在后台配置对象中，区分四组：Redis URL／连接池与超时，三类 TTL／大小上限，按域回源额度与 single-flight 限制，熔断阈值／探测预算。静态意图资源目录与模型编码配置属于识别器配置，不借 Redis 配置控制。

禁止在多个模块分别硬编码一套 TTL 或层层自动重试。参数越界、缺少版本或非法 URL 均显式诊断；无 Redis 配置意味着关闭 Redis 加速，不意味着关闭记忆或 RAG。

## 14. 模块接入与业务边界

| 模块 | 负责的部分 | 不负责的部分 |
| --- | --- | --- |
| MemoryManager | 保存原文、更新画像、提供带来源／版本的有效画像快照 | 不依赖 Redis 成功才能提交 SQL |
| 画像缓存适配器 | 在缓存层复用同用户画像；提前加载及请求读取走同一个入口 | 不生成／猜测画像，不读其他用户原文 |
| 缓存访问层（现有 VersionedCache 的后续扩展） | 完整 key、读状态、schema、TTL／大小、连接池、single-flight、回源预算及 Redis 熔断 | 不决定业务路由、不托管权威任务状态 |
| 查询 Embedding 适配器 | 复用相同实际输入及编码配置的向量 | 不把模板向量和用户查询向量混为同一版本／缓存对象 |
| RAG 适配器 | 复用完整正常检索证据；实际召回、融合、重排仍走既有管线 | 不增加 FAQ 或通用答案直返入口，不用失败推断政策不存在 |
| 意图识别器 | 初始化匹配的示例／向量／BM25 资源，实时计算输入的意图信号 | 不靠 Redis 存静态示例，不能伪造缺失分支分数 |
| PromptManager／Agent loop | 按需组装记忆及证据，处理繁忙／超时／降级并服从 Agent 总预算 | 不直接管理 Redis，不用缓存结果恢复不可见的私有轨迹 |

保持一份有效业务结果，缓存只参与加速。权限、scope 和必要的参数校验在缓存命中之前执行；命中之后再验证数据合同。当前 RAG 接口尚无完整的用户级缓存身份，后续接入需要从可信请求传递 owner_id，而非把它暴露为可任意指定的模型工具参数。

缓存只覆盖三类完整可复用读取，不在“工具统一入口＋RAG 内部＋Agent 输出”叠三层相同结果缓存。私有执行记录、最新会话问答与当前控制状态仍读原有运行时／MemoryManager；本轮明确要求优先于缓存旧画像。

用户输入向量缓存命中可跳过相同编码计算，但意图分数仍针对当前问题与当前示例资源计算；如果未来复用该向量给意图识别，只有实际编码配置完全一致才允许复用，不因向量维度相同就混用。

## 15. 实现后的验收方案

本节定义通过条件，不代表测试已经执行。当前请求只改设计文档，不能据此报告真实 Redis 连通、吞吐提升、成本降低或故障恢复通过。

### 15.1 不联网的自动化验证

使用受控内存／假 Redis、假时钟及模型桩，验证数据和异步行为，不消耗模型调用费用。

| 场景 | 必须满足的结果 |
| --- | --- |
| 正常命中与 TTL 到期 | 命中不回源；到期后一次加载；命中不续期，抖动范围正确 |
| empty 与 miss | empty 是可命中的成功空结果，miss 会回源；Embedding 无效向量不能成为 empty |
| 用户／配置隔离 | 换 owner_id、scope、输入、top_k、过滤或配置版本，不能串缓存；画像 snapshot_revision 不假装即时版本 |
| schema／缓存损坏 | 未知字段、错误类型、坏 JSON、错维度／非有限数值或 scope 不符不直接进入 prompt，转为受控回源 |
| 同 key 并发 | 完整身份相同的请求最多一份在途计算，等待者复用；不同 key 不互相占用一把全局锁 |
| 限额与截止时间 | 达到各域并发／排队／等待者上限不继续回源；排队、等待和执行共用截止时间 |
| 取消／异常清理 | 一个等待者取消不误杀其他等待者；无人使用的任务尽力取消，登记和额度正确释放 |
| Redis 超时与熔断 | 5 次符合定义的网络失败触发熔断；miss／empty／池满／坏 schema 不误触发；单探测恢复，迟到调用不改写新状态 |
| SQL 更新与陈旧边界 | 不主动双写；TTL 内旧画像是允许行为，本轮明确指令与最新会话不被旧画像覆盖 |
| 本地副本与大小 | 不超过条数及字节限额，不延长原快照寿命；超大正常结果跳过缓存但不破坏业务结果 |
| 提前加载与资源版本 | 当前用户画像不重复加载；静态示例映射／向量模型一致；已有向量不重算，未授权模式不触发在线构建 |
| 写缓存失败 | 有效结果仍可返回，SQL 已成功提交不回滚，副作用工具不重放 |

### 15.2 独立真实 Redis 集成验证

后续在独立临时测试实例及独立测试前缀执行，不对已有实例 FLUSHDB／FLUSHALL。使用模型桩，不需要付费模型。

- 验证真实 String／Hash 的写入、TTL、事务重建与读取合同，及 redis-py 配置下的实际连接协商／ACL。
- 验证 maxmemory／volatile-lru 在内存压力下的真实行为及写入失败处理；不把客户端字节估算当成服务端内存测量。
- 受控停／启动测试实例，验证超时、熔断、受控回源、空缓存恢复及不存在批量补热风暴。
- 验证无认证／越出项目命名空间／管理命令访问被拒绝，缓存不可用时用户权限检查仍有效。
- 检查后台资源关闭，不能遗留无限任务或连接；不能用测试清理命令删用户 SQL、Chroma、意图文件或其他项目缓存。

### 15.3 性能验证边界

分别比较关闭缓存、冷缓存和暖缓存，记录真实回源次数、完成耗时及模型调用数；加入重复与不重复问题，避免只用高重复样本制造漂亮命中率。之后在用户批准的在线模式下再验证真实 RAG／Embedding 效果。

暂不设文章中的 70% 命中率、300 ms 响应或 40% 成本节省作为验收承诺。只有重复请求确实减少回源、缓存开销可接受且答案／权限不受损时，才认可对应缓存的价值。

日志、链路追踪与长期监测留到全项目最后统一设计；这里的测试测量不提前引入生产监控平台。
