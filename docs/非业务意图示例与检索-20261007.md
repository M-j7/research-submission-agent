## 1. 示例与边界

原九类业务各五条，共45条，文件不改。新增 [non_business_templates.json](../src/submission_assistant/intent/data/non_business_templates.json)，C10共30条：

| 示例组 | 条数 | 代表性表达 |
|---|---:|---|
| 问候、一般交流 | 8 | 你好；您好，请问在吗；早上好；Hello! |
| 感谢、理解、结束对话 | 6 | 谢谢你的帮助；好的，我明白了；再见，下次再聊 |
| 助手能力与使用咨询 | 8 | 你能提供哪些帮助；助手支持哪些功能；怎样使用咨询助手 |
| 明确的范围外请求 | 8 | 天气、菜谱、旅游、笑话、无关代码任务、电影推荐 |

合计24条中文、6条英文。覆盖常见非业务交流，不可能枚举所有范围外话题；不是30个判定关键词，也不是完整评测集。

不收录“我的稿件出问题了”“这个怎么办”“帮我看看”等模糊表达。前者业务领域明确但需求不清，后者需要历史消歧，不能因为交通用 Agent 就都标成非业务。含“你好／谢谢”并同时询问费用、摘要等的消息，仍有业务诉求。

## 2. 当前如何使用

`load_templates()` 继续读取原45条业务例子，供当前 JEV 九类 choice 使用；`load_retrieval_templates()` 合并业务例子与C10供两路检索。校验类别、非空字符串、同类与跨类重复；C10示例数量可变，不要求只有五条。

BM25对全部75条建立本地索引；Embedding将全部75条生成向量，首次初始化按20、20、20、15分批。两路均按类别取最高匹配分及示例，输出十类原始分，不按示例数量相加。这里的 `selected_intent=C10` 仅为模板匹配第一名，不代表可靠的非业务结论或路由决定。

原业务融合公式仍只处理C01–C09，不给 JEV 虚构C10概率。检索C10的原始分、score_type与命中示例单列在融合输出的 `non_business_evidence`；完整原始十类分也在 `sources.embedding` / `sources.bm25` 中保留。不能把当前九类业务融合分与C10原始分直接比较；尚未实现十项独立判断及其融合。

JEV仍发送dialogue、clarity、intent三个问题，intent仍是九类单选。用户讨论的“九项业务＋一项非业务，各自判断是否相关，并保留清晰度”尚待单独实现。

## 3. 缓存与风险

- 新增C10改变了完整示例内容的指纹，因此后续首次真实Embedding调用会重新计算75条示例；旧缓存保留，不删除用户产物。后续可正常复用新缓存。修改C10内容同样会产生新指纹。
- 非业务30条、每个业务类五条，会提高C10遇到一个高分例子的机会。取最高分避免简单数量累加，但不消除最大值偏差；不能据此宣称C10更可信。
- 新增30条也改变了BM25全库词频、文档频率与平均长度，原业务分值会变化，不能沿用旧分数阈值。
- “好的／谢谢”在特定历史里可能是确认或承接；两路当前只看本轮文本，不负责消歧。范围外长尾话题也可能更像某类业务，因此仍需独立判断与清晰度信息。

## 4. 离线烟雾观察

9条人工合成消息，只调用本地BM25，没有付费模型调用：

| 问句 | 匹配第一名 | 解释 |
|---|---|---|
| 您好，能聊一下吗？ | C10 | 命中问候 |
| 谢谢你的耐心解释 | C10 | 命中感谢 |
| 你可以提供哪些帮助？ | C10 | 命中能力咨询 |
| 今天北京天气怎么样？ | C10 | 命中另一地点的天气示例 |
| 摘要的字数限制是多少？ | C02 | 业务候选保留 |
| 你好，摘要最多多少词？ | C02 | 此例业务匹配高于问候 |
| 谢谢，发表费用是多少？ | C07 | 此例业务匹配高于感谢 |
| 我的稿件出问题了 | C09 | 无法据此确认是撤稿；需检查清晰度 |
| 这个怎么办？ | C10 | 错误候选，命中“这个助手支持哪些功能”的通用片段 |

最后一例说明：没有把无指代句加入C10，不代表检索不会错配C10。需要保留命中示例，让JEV／后续路由识别这是通用措辞造成的弱证据，不能自动当作非业务。没有用临时关键词规则修饰输出。

[完整BM25输出](实测结果/20261007-non_business_bm25.json) 保存九条的原始分与命中示例。Embedding仅做了受控向量几何的离线接口测试，证明C10会发送、还原、算分与输出；没有做真实Qwen分类质量验证，不报告准确率。
